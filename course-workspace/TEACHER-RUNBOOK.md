# 教师运行手册

这份手册给老师使用，目标是把 Slides、学生页和 Codex 任务串成一条现场可执行的课程。它不替代各 Unit 的 `STUDENT.md` 和 `AGENT-TASK.md`。

## 当前判断

7 月 11 日的一日 pilot 证明方向成立，但不能写成 Unit 0-5 已完整通过。真实问题主要在三处：

- Slides、学生页、Agent 任务和老师讲解没有足够紧密地咬合。
- Unit 2 的文章编译没有经过共同拆文和结果审查，导致 Unit 3 的 Skill 写作缺少自然起点。
- 学生基础差异很大；零基础学生需要更短的步骤、更多现场关注和更早的降级路径。

下一版优先按两日主线准备，一日课只作为 lite 版本。

## 基本教学节奏

每个教学段都按同一节奏组织：

```text
老师讲 5-10 分钟
-> 学生做一个小动作
-> Codex 执行一个小任务
-> 学生亲自检查一个结果
-> 老师抽象出一条原则
```

不要让学生长时间只复制提示词、等待 Codex 或看老师排障。任何一个 Agent 操作结束后，都要让学生打开一个文件、页面或报告，亲自判断结果是否可接受。

## 课前

使用 [课前准备矩阵](PREFLIGHT-MATRIX.md)，不要只看口头确认。

必须重点检查：

- 浏览器、Codex、Terminal 三条路径都能访问 GitHub。
- GitHub 账号没有邮箱、验证码或风控阻断。
- Obsidian 有长期个人 Vault，而不是临时课程文件夹。
- Web Clipper 使用课程模板，Raw 能落到 `Inbox/Raw/`。
- 课程 workspace 只读，个人产物写入 `Learn/Agent 101/`。

课前每个学生准备 5-10 个兴趣网页。课堂第一天优先使用这些网页，而不是直接把难文章当作核心材料。

## 两日主线

### Day 1：个人知识工作流

目标：

```text
把自己感兴趣的一组网页
变成可以在 Obsidian 里继续积累的小型 Wiki
```

建议顺序：

1. 验证 Unit 0 结果：Codex、GitHub、Obsidian、课程 workspace、两个基础 Skill。
2. 简讲 Agent + Markdown + Obsidian 的工作系统。
3. 用学生兴趣链接抓取一篇 Raw，并共同检查 frontmatter 和正文。
4. 老师带学生共同拆一篇浅文章：观点、概念、实体、来源、不确定点。
5. Codex 编译这一篇到 `Learn/Wiki/`。
6. 学生亲自检查 Raw、拆文卡、Index 和一页知识内容。
7. Codex 根据学生反馈修正一次，学生再打开 Log 确认记录。
8. 用拆文卡、Wiki 变化、人的修正和 Log 建立 Skill 证据卡；时间足够再写 mini Skill 草稿。

最低完成：

- 每个学生至少有一篇自己兴趣文章完成人审查过的 Wiki 编译。
- 能说清 Raw 为什么只读，Wiki 为什么需要 Index 和 Log，人为什么必须检查。
- Skill 最少可以只是草稿；不要强行追求完整安装和批量运行。

### Day 2：Vibe Coding 与项目表达

目标：

```text
用预制 AI Pet Demo
体验一次可见、可验证、可继续合作的小项目开发
```

建议顺序：

1. 跑起 AI Pet mock 基线，让学生先看见页面。
2. 解释组件、皮肤、气泡、mock、真实 API 的职责。
3. 每个学生选择一个与兴趣相关的小改动。
4. Codex 先解释准备改哪些文件，再等学生确认。
5. 完成页面可见改动，运行检查和浏览器验证。
6. 有条件时接入真实模型回复。
7. 时间足够再做 fork、branch、Pull Request；账号阻断时不强推。
8. 用 Unit 5 把学生自己的想法整理成需求文档，作为课后继续入口。

最低完成：

- 每个学生看到一个自己参与决定的页面可见变化。
- 至少一次模型回复路径被学生亲自验证；如果真实 API 阻断，必须写明阻断原因。
- 每个学生留下验证报告或项目需求文档。

## 一日 lite 版本

一日课不要承诺覆盖所有 Unit。只保留两个体验目标：

1. Agent + Markdown + Obsidian 的个人知识工作流。
2. AI Pet Demo 的页面可见改动。

在一日课中：

- Unit 3 Skill 写作只做概念展示或草稿，不作为完成标准。
- GitHub Pull Request 只在账号稳定、时间充足时做。
- Unit 5 只做需求澄清入口，不要求实现项目。

## Unit 运行提示

| Unit | 老师重点 | 容易出错 | 现场处理 |
| --- | --- | --- | --- |
| Unit 0 | 验证真实环境，不重复安装 | Terminal 代理、GitHub 账号、Claudian 插件 | 按矩阵逐项检查；Claudian 失败可直接用 Codex 继续 |
| Unit 1 | 让学生提出真实问题 | 难文章变成被动听讲 | 零基础学生先用兴趣文章；Karpathy 可作为方法参考 |
| Unit 2 | 人先拆文，再让 Agent 编译 | Agent 直接编译，学生看不懂判断标准 | 必须共同拆一篇，之后才运行 Codex |
| Unit 3 | 从 Unit 2 证据提炼 Skill | 没有拆文卡、人工修正和 Log 就空写 Skill | 先完成证据卡；Unit 2 不完整时，不起草、不启用 |
| Unit 4 | 先看见页面，再改小目标 | 从零开发、同时改太多、GitHub 阻断 | 使用预制 demo；先本地可见，再考虑 GitHub |
| Unit 5 | 想法先变需求，代码可延后 | Codex 马上开写 | 最低产物是 `PROJECT-REQUIREMENTS.md` |

## 对不同基础学生的处理

高主动性学生：

- 可以让他更早承担探索、皮肤、主题或小功能改造。
- 要求他解释选择理由和验证证据，避免只追求“做出来”。

零基础学生：

- 每一步只给一个目标，避免同时处理账号、命令、文件和概念。
- Codex 长时间运行或连续失败时，老师要主动介入排障。
- 给更短的成功路径，例如打开文件、确认来源、改一句文案、验证一个页面状态。
- 不把 GitHub Pull Request 作为必达目标；账号阻断时用本地结果完成体验。

## 现场故障降级

| 故障 | 不要做 | 降级路径 |
| --- | --- | --- |
| GitHub 账号风控 | 不在主线里长时间等待验证 | 用公开 repo 只读材料和本地代码体验继续 |
| Terminal 不走代理 | 不把 Codex 可用当作 Terminal 可用 | 记录错误；优先使用浏览器或已 clone repo；课后修代理 |
| Web Clipper 字段缺失 | 不让 Agent 因 schema 直接卡死 | 修模板或做一次字段 normalize 后继续 |
| Skill 看不到 | 不假装已调用 Skill | 记录未验证；新开 task 或重启后再试 |
| API key / 额度 / 网络失败 | 不把 mock 当真实 API 完成 | 保留 mock 基线，记录真实 API 阻断 |
| Codex 长时间失败 | 不让学生只等命令 | 老师切换到解释、人工检查或更小任务 |

## 每个教学段的证据

老师每段结束时至少收一类证据：

- 一个 Obsidian 文件路径。
- 一个 Git 命令或检查命令结果。
- 一个网页可见结果。
- 一个学生亲自确认的判断。
- 一个仍未验证或需要协助的阻断项。

材料存在不等于完成。没有真实学生操作、文件、页面或人工检查，就保持“未验证”。

## 下次改版优先级

1. 把 Day 1 从难文章主线改成兴趣文章主线。
2. Unit 2 增加共同拆文章的显式步骤和输出模板。
3. Unit 3 已增加证据卡和逐篇拆文确认；下一步做真实单篇 forward test。
4. Unit 4 明确本地体验和 GitHub PR 两条完成线。
5. Unit 5 放到第二天或课后，不再塞进一日主线。
