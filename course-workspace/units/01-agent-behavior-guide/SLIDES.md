# 普通文件问答的问题

把文件交给聊天 AI 后，它通常会：

```text
收到问题
→ 找到相关片段
→ 临时组合答案
→ 对话结束
```

文件还在，但这次形成的新理解不一定被保存。

---

# LLM Wiki 多了一层

```text
Raw：原始资料
只读，保留原貌
        ↓
Wiki：整理后的知识
持续更新、互相链接
        ↓
人：阅读、提问、判断
```

关键不是回答更多，而是让有价值的知识继续积累。

---

# 三层架构

| 层 | 保存什么 | 怎样使用 |
| --- | --- | --- |
| Raw | 文章、论文、图片、数据 | 人选择；Agent 只读 |
| Wiki | 摘要、概念、实体、比较和关联 | Agent 维护；人阅读检查 |
| Schema | 目录、命名、格式和流程规则 | 人与 Agent 一起完善 |

Schema 可以写在 `AGENTS.md` 这样的说明文件中。

---

# Wiki 里可能有哪些页面

```text
Summary
一份来源主要讲了什么

Concept
一个概念在多份来源中怎样发展

Entity
人物、组织、工具或项目的信息

Index / Cross-reference
页面在哪里，它们怎样互相连接
```

它们不是每篇文章都必须机械生成的固定字段。

---

# 三种操作

| 操作 | 用人话解释 |
| --- | --- |
| Ingest | 加入新资料，并更新相关知识页 |
| Query | 针对 Wiki 提问，把有价值的答案写回 |
| Lint | 检查矛盾、过期内容、孤立页面和缺口 |

只有持续更新和检查，Wiki 才不会变成一堆旧文件。

---

# Index 和 Log 不一样

```text
index.md
现在有哪些知识？去哪里找？

log.md
什么时候加入了什么？最近做过什么？
```

Index 面向内容，Log 面向过程。

---

# 人和 Agent 怎样分工

人负责：

- 选择值得保存的资料；
- 提出真正关心的问题；
- 判断解释是否可信；
- 决定什么值得长期保留。

Agent 负责摘要、归档、关联、更新和其他重复维护工作。

---

# 一个具体例子

连续阅读三篇关于 AI Agent 的文章：

```text
第 1 篇 → 建立来源摘要和 Agent 概念页
第 2 篇 → 更新概念页，补充工具实体页
第 3 篇 → 标出不同作者的矛盾，形成比较页
```

三次阅读不是三份孤立总结，而是在维护同一套知识。

---

# 为什么 Obsidian 合适

- Markdown 文件对人和 Agent 都可读；
- 页面之间可以互相链接；
- 修改结果可以立刻打开检查；
- 关系图可以看到知识怎样连接；
- 文件可以用 Git 保存历史。

Obsidian 是载体，真正重要的是可见、可改、可积累的文件。

---

# Unit 1 的四个结论

1. 普通文件问答不等于知识已经积累。
2. LLM Wiki 在 Raw 和人之间增加了长期维护的知识层。
3. Schema 让 Agent 知道应该怎样维护这套知识。
4. 人负责方向和判断，Agent 负责重复维护。
