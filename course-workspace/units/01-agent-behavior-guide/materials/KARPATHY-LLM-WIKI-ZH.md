# LLM Wiki

一种使用大语言模型（LLM）搭建个人知识库的方法。

这是一份“想法说明”。你可以把它复制给自己的 LLM Agent，例如 OpenAI Codex、Claude Code、OpenCode / Pi 等。它的任务是讲清楚整体思路，具体怎样实现，则由你和 Agent 一起决定。

> 说明：这份中文译文为了课堂阅读做了通顺化处理，但保留了原文的章节结构和核心含义。如需核对细节，请回到同目录的英文原文。

## 核心想法

大多数人与 LLM 一起使用文档时，体验很像检索增强生成（RAG）：你上传一组文件，LLM 在收到问题时找出相关片段，再生成答案。这种方式能用，但每次提问时，LLM 都要从头重新发现知识。如果一个细微的问题需要综合五份文档，LLM 每次都要重新寻找、拼接相关片段，之前的理解并没有积累下来。NotebookLM、ChatGPT 文件上传和大多数 RAG 系统都是这样工作的。

这里提出的是另一种方法。LLM 不只在提问时从原始文档中检索内容，而是**逐步建立并维护一套长期存在的 Wiki**。这套 Wiki 是一组结构清楚、互相链接的 Markdown 文件，位于你和原始资料之间。加入一份新资料时，LLM 不只是给它建立索引，等以后再找；它会阅读资料、提取关键信息，并把新内容整合进已有 Wiki。它可能更新实体页面、修订主题摘要、标出新旧说法的矛盾，并加强或挑战正在形成的综合结论。知识只需被“编译”一次，之后持续保持更新，而不是每次提问都重新推导。

关键区别是：**Wiki 是一份长期存在、能够不断增值的成果。** 页面之间的引用已经建立，矛盾已经被标出，综合结论已经反映目前读过的全部资料。每增加一份来源、每提出一个好问题，Wiki 都会变得更丰富。

你通常不需要亲自编写 Wiki，LLM 会负责写作和维护。人负责选择资料、探索方向和提出好问题。LLM 负责摘要、交叉引用、归档和记录等重复工作，让知识库经过较长时间后仍然有用。作者的实际做法是：一边打开 LLM Agent，一边打开 Obsidian。LLM 根据对话修改文件，人则实时浏览结果、沿链接阅读、检查关系图和更新后的页面。可以把 Obsidian 看成集成开发环境（IDE），把 LLM 看成程序员，把 Wiki 看成代码库。

这种方法可以用在很多场景，例如：

- **个人成长**：跟踪目标、健康、心理和自我提升，把日记、文章、播客笔记等资料逐步整理成对自己的结构化认识。
- **专题研究**：用几周或几个月深入研究一个主题，持续阅读论文、文章和报告，并逐步建立一套完整 Wiki 和不断发展的观点。
- **阅读一本书**：读完一章就把它加入系统，逐步建立人物、主题、情节线索以及它们之间的关系。读完时，你会得到一套丰富的伴读 Wiki。可以想象 [Tolkien Gateway](https://tolkiengateway.net/wiki/Main_Page) 这类粉丝 Wiki，只不过交叉引用和维护工作由 LLM 协助完成。
- **团队或企业**：用 Slack 讨论、会议记录、项目文档和客户通话喂给 LLM，由它维护内部 Wiki，也可以由人复核更新。这样，那些团队成员通常不愿意做的维护工作就不会被长期搁置。
- **竞争分析、尽职调查、旅行规划、课程笔记和兴趣研究**：只要知识会持续增加，而且你希望它被组织起来而不是散落各处，就可以使用这种方法。

## 架构

系统分成三层：

**原始资料（Raw sources）**：由你选择和保存的来源文件，例如文章、论文、图片和数据文件。它们不可随意改动。LLM 可以读取，但不能修改。这一层是事实来源。

**Wiki**：一个存放 LLM 生成的 Markdown 文件的目录，其中可以有摘要页、实体页、概念页、比较、总览和综合分析。LLM 负责这一层的创建和维护。加入新资料时，它会更新相关页面、维护交叉引用，并让内容保持一致。人阅读和检查，LLM 写作和维护。

**规则说明（Schema）**：一份告诉 LLM 如何工作的文档，例如 Claude Code 使用的 `CLAUDE.md`，或者 Codex 使用的 `AGENTS.md`。它说明 Wiki 的结构、写作规范，以及加入资料、回答问题和维护 Wiki 时应该遵循的流程。这是最关键的配置文件：它让 LLM 成为一个有纪律的 Wiki 维护者，而不只是普通聊天机器人。随着经验增加，人和 LLM 可以共同修改这份规则。

## 三种操作

**导入（Ingest）**：把一份新资料放进 Raw 后，告诉 LLM 处理它。一个可能的流程是：LLM 阅读资料，与你讨论要点，在 Wiki 中写一页摘要，更新索引，更新有关的实体页和概念页，再在日志里追加记录。一份资料可能会影响 Wiki 中 10 到 15 个页面。作者更喜欢一次导入一份资料，并持续参与：阅读摘要、检查更新、告诉 LLM 什么更值得强调。也可以一次批量导入很多资料，只是人工监督会少一些。应该根据自己的习惯设计流程，并把它写进 Schema，供以后的会话继续使用。

**查询（Query）**：针对 Wiki 提问。LLM 先搜索相关页面，阅读它们，再生成带来源的综合答案。答案可以是 Markdown 页面、比较表、Marp 幻灯片、图表或画布。重要的是：**好的答案也可以作为新页面写回 Wiki。** 一次有价值的比较、分析或新发现，不应该消失在聊天记录里。这样，提问产生的新认识也会像导入的资料一样持续积累。

**体检（Lint）**：定期让 LLM 检查 Wiki 的健康状况，例如：页面之间是否互相矛盾；旧说法是否已被新来源取代；是否有没人链接到的孤立页面；重要概念是否被反复提到却没有自己的页面；是否缺少交叉引用；是否存在可以通过网络搜索补上的资料缺口。LLM 也擅长提出接下来值得研究的问题和可能需要的新来源。这能让 Wiki 在增长过程中保持健康。

## 索引和日志

随着 Wiki 变大，两份特殊文件可以帮助 LLM 和人找到内容。它们的用途不同：

**`index.md` 面向内容。** 它是 Wiki 的目录，列出每个页面的链接、一句话说明，以及可选的日期、来源数量等信息。可以按实体、概念、来源等类别组织。每次 Ingest 时，LLM 都更新它。回答问题时，LLM 先读索引，找到相关页面，再深入阅读。在中等规模下，大约 100 份来源、几百个页面，这种方式通常已经很好用，不一定需要基于向量的 RAG 基础设施。

**`log.md` 面向时间。** 它是一份只追加、不回头改写的记录，写明什么时候发生了什么，例如 Ingest、Query 和 Lint。一个实用技巧是让每条记录使用统一开头，例如 `## [2026-04-02] ingest | 文章标题`。这样可以用简单的 Unix 工具处理日志，例如 `grep "^## \[" log.md | tail -5` 可以查看最近五条记录。日志展示 Wiki 的演变过程，也帮助 LLM 了解最近做过什么。

## 可选：命令行工具

当 Wiki 变大后，可以制作一些小工具，让 LLM 更高效地操作它。最明显的是 Wiki 页面搜索工具。规模很小时，`index.md` 已经够用；规模变大后，则需要更完整的搜索。[qmd](https://github.com/tobi/qmd) 是一个选择：它是在本地运行的 Markdown 搜索引擎，结合 BM25、向量搜索和 LLM 重排序。它既有命令行界面，方便 LLM 调用，也有 MCP Server，可以作为 Agent 的原生工具。你也可以在真正需要时，让 LLM 帮忙通过 Vibe Coding 写一个更简单的搜索脚本。

## 实用技巧

- **Obsidian Web Clipper** 是一个浏览器扩展，可以把网页文章转成 Markdown，适合快速把资料放进 Raw。
- **把图片下载到本地。** 在 Obsidian 的“设置 -> 文件与链接”中，把附件目录设为固定位置，例如 `raw/assets/`。再到“设置 -> 快捷键”中搜索 Download，为“下载当前文件的附件”设置快捷键，例如 `Ctrl+Shift+D`。抓取文章后按快捷键，图片就会下载到本地。这样，LLM 可以直接查看和引用图片，不必依赖可能失效的网址。需要注意，LLM 通常不能在一次读取中同时理解 Markdown 正文和其中的所有内嵌图片。可以让它先读文字，再分别查看部分或全部图片来补充上下文。
- **Obsidian 的关系图谱**适合观察 Wiki 的形状，例如哪些页面彼此连接、哪些页面是中心、哪些页面是孤立的。
- **Marp** 是一种用 Markdown 编写幻灯片的格式，Obsidian 也有对应插件，适合直接从 Wiki 内容生成演示文稿。
- **Dataview** 是一个 Obsidian 插件，可以根据页面的 frontmatter 运行查询。如果 LLM 给 Wiki 页面添加了 YAML frontmatter，例如标签、日期和来源数量，Dataview 就能生成动态表格和列表。
- Wiki 本质上就是一个由 Markdown 文件组成的 Git repo，因此可以获得版本历史、分支和协作能力。

## 为什么这种方法有效

维护知识库最麻烦的部分，不是阅读和思考，而是整理工作：更新交叉引用、让摘要保持最新、记录新资料怎样推翻旧说法，以及让几十个页面彼此一致。人常常放弃 Wiki，是因为维护成本增长得比价值更快。LLM 不会因为重复工作感到厌烦，也不会忘记更新交叉引用，而且一次可以修改 15 个文件。维护成本接近于零，Wiki 才有机会长期保持更新。

人的工作是选择资料、指引分析方向、提出好问题，并思考这些内容到底意味着什么。其他重复工作可以交给 LLM。

这个想法在精神上与 Vannevar Bush 于 1945 年提出的 Memex 有关：一种由个人维护的知识存储系统，文档之间有可以追踪的关联路径。Bush 的设想比后来出现的互联网更接近这里所说的系统：它是私人的、主动整理的，而且文档之间的连接与文档本身同样有价值。当时没有解决的问题是“谁来维护”；现在可以由 LLM 承担这部分工作。

## 说明

这篇文章有意保持抽象。它描述的是一种方法，而不是某个固定实现。具体目录怎样设计、Schema 使用什么规范、页面采用什么格式、需要哪些工具，都取决于你的研究领域、个人偏好和所使用的 LLM。上面提到的内容都是可选和可组合的：有用的就采用，不需要的就忽略。

例如，你的资料可能只有文字，因此不需要处理图片；Wiki 可能很小，因此只用索引文件就足够，不需要搜索引擎；你也可能不需要幻灯片，只想保留 Markdown 页面；输出格式也可以完全不同。正确的使用方式，是把这份想法说明交给自己的 LLM Agent，再与它一起做出适合自己的版本。这篇文章只负责讲清楚模式，具体实现可以由你和 LLM 继续完成。
