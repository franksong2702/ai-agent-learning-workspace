# Unit 2

## 从兴趣文章开始第一次 Wiki 编译

先抓一篇你真的愿意看的文章，再把它变成可以长期积累的 Obsidian Wiki。

---

# 兴趣文章先行

这节课不要从抽象方法开始。

```text
喜欢的偶像 / 游戏 / 工具 / AI 新闻 / 学习方法
        ↓
一篇具体网页
        ↓
Web Clipper 保存 Raw
```

文章不需要很深，但必须能让你说出：我为什么想看它？

---

# Karpathy 是参考，不是第一座山

Unit 1 的 Karpathy 文章提供了方法语言：

```text
Raw / Wiki / Schema / Ingest / Query / Lint
```

Unit 2 只在需要时回看它。真正的课堂输入，是今天这篇兴趣文章。

---

# Web Clipper 是硬前置

进入编译前，必须看到一个真实文件：

```text
个人 Obsidian Vault
└── Inbox/
    └── Raw/
        └── 一篇新文章.md
```

文件要有正文、原始链接和抓取日期。只有网页链接，不算准备完成。

---

# 先拆文，再编译

不要一开始就让 Agent 生成 Wiki。

```text
先一起读这篇文章
再把判断写进拆文卡
最后让 Agent 根据判断编译
```

这一步决定后面的 Wiki 是你的理解，还是机器的一次自动摘要。

---

# 拆文模板让判断外显

拆文卡至少回答：

- 我为什么选这篇文章；
- 一句话主旨是什么；
- 哪些是事实，哪些是观点；
- 哪些概念和实体值得以后再找；
- 哪些地方还不确定；
- 是否值得进入 Wiki。

没有这个中间层，Agent 很容易把“看起来完整”误当成“真的理解”。

---

# Raw 保持只读

```text
Inbox/Raw/
事实来源，只读

Learn/Agent 101/Unit 2/
拆文卡，可以修改和确认

Learn/Wiki/
长期知识层，可以创建和更新
```

如果解释错了，修拆文卡或 Wiki；不要回头改写原始文章。

---

# Agent 负责编译，不负责替你判断兴趣

Agent 可以做：

- 检查 Raw 和来源；
- 创建拆文卡草稿；
- 根据确认过的拆文编译 Wiki；
- 建立规则、索引、日志和来源知识页；
- 标出不确定点。

但“这篇文章为什么值得看”，必须由人先说清楚。

---

# 最小 Wiki 只要求四种职责

| 职责 | 要解决的问题 |
| --- | --- |
| 规则说明 | 以后应该怎样维护这套 Wiki？ |
| 索引 | 现在有哪些知识，去哪里找？ |
| 日志 | 什么时候处理了什么，发生了哪些变化？ |
| 知识页面 | 这篇来源带来了什么可复用内容？ |

具体文件名和目录由 Agent 设计并记录。

---

# 不要为了整齐制造空页面

Summary、Concept、Entity、Comparison 都是可选的页面类型。

```text
有长期价值 → 创建或更新
只是文章里顺便提到 → 留在来源摘要
已有同一概念 → 更新旧页面
没有可靠依据 → 标记不确定
```

页面数量不是质量指标。

---

# Agent 做完以后必须汇报

汇报需要回答：

- 读了哪份 Raw；
- 拆文卡里哪些判断进入了 Wiki；
- 创建或更新了哪些文件；
- 每个文件为什么需要；
- 哪些页面没有创建以及原因；
- 哪些结论还不确定；
- Raw 是否保持不变。

“已经搞定”不是有效汇报。

---

# 人检查四类证据

```text
Raw
确认来源没有被改写

Decomposition
确认拆文判断说得通

Index
确认新知识能够找到

一页知识内容
确认有来源、读得懂、值得保留
```

然后明确给出：保留、修改或不确定。

---

# 一次修正让闭环完整

```text
Web Clipper 抓取 Raw
→ 人和 Agent 共同拆文
→ Agent 创建或更新 Wiki
→ Agent 汇报
→ 人打开文件检查
→ Agent 根据反馈修正
→ Log 记录真实变化
```

到这里，第一次编译 loop 才真正走完。

---

# 下一单元才把方法写成 Skill

Unit 3 会回看：

- 这次选择兴趣文章的方式；
- 这张拆文卡；
- Agent 实际做过的步骤；
- Wiki 中真实产生的文件变化；
- 人提出的修正；
- 哪些边界以后必须稳定保留。

再使用 `writing-great-skills`，把成功运行过的流程固化成自己的 Skill。
