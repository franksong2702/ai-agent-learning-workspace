# Unit 2

## 让 Agent 设计并完成第一次 Wiki 编译

不从空白编写复杂提示词，让 Agent 阅读现成方法并完成真实任务。

---

# Unit 1 留下了一份可用的方法

Karpathy 的文章已经讲清楚：

```text
Raw 保存原始资料
Wiki 积累整理后的知识
Schema 约束结构和维护方法
Ingest / Query / Lint 让系统持续运转
```

Unit 2 不重新讨论概念，而是把它真正运行一次。

---

# 这次只给 Agent 两份材料

```text
方法参考
Karpathy 的 LLM Wiki 文章

待处理来源
Web Clipper 保存的一篇新 Raw
```

方法文章告诉 Agent“怎么做”，新 Raw 告诉 Agent“这次处理什么”。

---

# Web Clipper 是硬前置

进入编译前，必须看到一个真实文件：

```text
个人 Obsidian Vault
└── Inbox/
    └── Raw/
        └── 一篇新文章.md
```

文件要有正文、原始链接和抓取日期。只有网页链接，不算准备完成。

---

# 人只需要确认四件事

1. 个人 Obsidian Vault 在哪里；
2. 新 Raw 文件在哪里；
3. Raw 的原始文章链接是什么；
4. Wiki 的输出根目录是 `Learn/Wiki/`。

不需要先画目录，也不需要先填写 Schema 表格。

---

# Agent 负责设计和执行

Agent 需要自己判断：

- 当前是否已经有 Wiki 结构；
- 哪些目录和文件真正必要；
- 新建页面还是更新已有页面；
- 哪些概念或实体值得长期保留；
- 怎样记录来源、索引和本次变化。

这就是 Agent 与普通聊天 AI 的区别之一。

---

# 最小 Wiki 只要求四种职责

| 职责 | 要解决的问题 |
| --- | --- |
| 规则说明 | 以后应该怎样维护这套 Wiki？ |
| 索引 | 现在有哪些知识，去哪里找？ |
| 日志 | 什么时候处理了什么，发生了哪些变化？ |
| 知识页面 | 这篇来源带来了什么可复用内容？ |

具体文件名和目录由 Agent 设计并记录。

---

# 不要为了整齐制造空页面

Summary、Concept、Entity、Comparison 都是可选的页面类型。

```text
有长期价值 → 创建或更新
只是文章里顺便提到 → 留在来源摘要
已有同一概念 → 更新旧页面
没有可靠依据 → 标记不确定
```

页面数量不是质量指标。

---

# Raw 必须保持不变

```text
Inbox/Raw/
事实来源，只读

Learn/Wiki/
Agent 可以创建和更新的知识层
```

如果解释错了，修 Wiki；不要回头改写原始文章。

---

# Agent 做完以后必须汇报

汇报需要回答：

- 读了哪份方法和哪份 Raw；
- 创建或更新了哪些文件；
- 每个文件为什么需要；
- 哪些页面没有创建以及原因；
- 哪些结论还不确定；
- Raw 是否保持不变。

“已经搞定”不是有效汇报。

---

# 人要亲自打开三个文件

```text
Raw
确认来源没有被改写

Index
确认新知识能够找到

一页知识内容
确认有来源、读得懂、值得保留
```

然后明确给出：保留、修改或不确定。

---

# 一次修正让闭环完整

```text
Web Clipper 抓取 Raw
→ Agent 阅读方法并设计
→ Agent 创建或更新 Wiki
→ Agent 汇报
→ 人打开文件检查
→ Agent 根据反馈修正
→ Log 记录真实变化
```

到这里，第一次编译 loop 才真正走完。

---

# 下一单元才把方法写成 Skill

Unit 3 会回看：

- 这次使用的简短提示词；
- Agent 实际做过的步骤；
- Wiki 中真实产生的文件变化；
- 人提出的修正；
- 哪些边界以后必须稳定保留。

再使用 `writing-great-skills`，把成功运行过的流程固化成自己的 Skill。
