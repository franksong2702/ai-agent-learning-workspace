# Unit 5：Codex 执行合同

## 任务目标

使用 `grill-me` / `grilling` 与人逐步澄清模糊想法，形成一份经人确认、可交给 Codex 实施的 `PROJECT-REQUIREMENTS.md`。

课堂最低完成只要求需求文档。实施路径和第一个可见结果属于明确选择后的扩展，不得为了显得完整而抢先开发。

## 开始前确认

1. 读取同目录 `STUDENT.md` 和 `templates/PROJECT-REQUIREMENTS.md`。
2. 确认 `grill-me` 与 `grilling` 均可用；`grill-me` 是入口，实际追问规则来自 `grilling`。
3. 请人用原话说出想法，不要求先改写成专业需求。
4. 确认个人 Obsidian 知识库绝对路径，以及唯一允许写入的个人项目目录。
5. 课程 repo 始终只读。目标文件已存在时停止并报告，不覆盖。

## 第一阶段：Grill Me 追问

- 一次只问一个问题，等待回答后再继续。
- 每个问题给一个推荐答案和简短理由，并明确允许采用、修改或否定。
- 根据已有回答选择下一问，不机械照抄固定问卷。
- 能从已授权文件中确认的事实，先读取，不重复询问。
- 优先解决会改变第一版目标、范围、验收或实现方向的问题。
- 回答“不知道”时，提供一个容易撤回的建议，或把它记录为需要在实施中验证的问题；不得编造事实。

必须达到的共同理解：

1. 想改变的问题或现状。
2. 使用者与使用场景。
3. 第一版可见结果。
4. 第一版必须具备的能力。
5. 明确不做的内容。
6. 已有材料、工具、设备、时间和其他限制。
7. 可被观察或检查的验收标准。
8. 会影响实施但可以通过第一步验证的未知项。

## 停止追问的条件

当上述八项已经足够让另一个新 Codex task理解并规划第一版时，主动建议停止追问。不要为了覆盖所有细节继续询问低影响问题。

出现以下任一情况时继续追问：

- 第一版结果仍无法描述为一个能看见、打开、阅读或操作的东西。
- “必须做”和“以后可能做”仍混在一起。
- 验收标准只能写成“感觉不错”“足够智能”或“好用”。
- 某个未确认假设会直接改变第一版是否成立。

## 写文件前的确认门

生成正式文件前，用人话复述：

- 已确认的目标、使用者、场景和第一版结果；
- 必须能力与不做范围；
- 已知限制；
- 验收方式；
- 待验证问题；
- 推荐的第一版边界。

最后只问：“这份理解是否准确？请指出要改的一处，或明确确认。”

未得到明确确认时，不生成正式需求文档。

## 生成需求文档

得到确认后：

1. 使用 `templates/PROJECT-REQUIREMENTS.md`。
2. 写入 `<个人 Obsidian 知识库>/Learn/Agent 101/Projects/<项目名>/PROJECT-REQUIREMENTS.md`。
3. 已确认内容写成决定；不确定内容写入“待验证问题”，不得伪装成要求。
4. 必须能力使用可检查的表述，不堆砌功能数量。
5. 验收标准对应第一版结果和每项必须能力。
6. 写完后请人亲自检查，并至少完成一次删除、改写或明确保留。

## 可选的实施交接

只有人在需求文档确认后明确要求继续，才进入此阶段。优先建议新开 Codex task，减少访谈上下文干扰实施。

新的 Codex task 必须：

1. 读取 `PROJECT-REQUIREMENTS.md`。
2. 检查已有项目事实；没有项目时先提出最小项目位置和形式，不直接创建。
3. 区分需求、当前事实和待验证假设。
4. 先生成 `PROJECT-PATH.md` 与 `NEXT-TASK.md`，推荐一个最小、可逆、可检查的步骤。
5. 解释准备修改的文件和验证方式，等人确认后才实施。
6. 时间不足时停在实施路径，不把“没有编码”报告为失败。

## 允许动作

- 读取当前 Unit、Skill 说明和人明确授权的项目文件。
- 单问单答并给出可否定的建议。
- 在确认后的个人项目目录创建或修改 Unit 5 产物。
- 根据人工反馈缩小范围、改写需求和验收标准。

## 禁止动作

- 不一次提出多个问题。
- 不无限追问低影响细节。
- 不在共同理解确认前生成正式需求文档。
- 不替人编造目标、使用者、来源、数据、限制或验收结果。
- 不把未来设想都塞进第一版。
- 不在第一阶段创建代码 repo、批量写代码或声称项目已完成。
- 不覆盖、删除、commit 或 push，除非后续获得针对当前动作的明确授权。
- 不把个人需求、私人材料或项目代码写入课程 repo。
