# Unit 5

## 把模糊想法变成可实施的需求

最后一课，从自己的想法出发。

---

# 模糊不是问题

```text
我想做一个个人网站
我想做一个语音笔记工具
我想让 AI 帮我整理学习
```

这些都可以成为起点。

真正的问题是：还没有说清楚第一版给谁用、做什么、怎样算完成。

---

# 不要让 Codex 立刻开做

想法还模糊时直接开发，常见结果是：

- 做出很多你没有要求的功能；
- 页面很好看，但解决的不是你的问题；
- 项目越来越大，没有清楚的完成位置；
- Codex 说“完成了”，你却不知道该检查什么。

先把高影响决定问清楚，再实施。

---

# Grill Me：一次只解决一个分歧

```text
提一个问题
→ 给一个推荐和理由
→ 由人采用、修改或否定
→ 根据答案决定下一问
```

它不是固定问卷，也不替人决定目标。

---

# 追问不是越多越好

追问到这些内容足够支持第一版，就应该停：

1. 为谁解决什么问题；
2. 第一版能看见什么；
3. 必须做到什么；
4. 明确不做什么；
5. 怎样检查结果；
6. 哪些未知问题留给小实验。

低影响细节可以等看到第一版后再决定。

---

# 不知道，也可以成为答案

```text
已经决定的内容 → 写成需求
还不知道的内容 → 写成待验证问题
以后可能想做 → 写进明确不做
```

需求文档不是假装什么都知道，而是把决定和未知分开。

---

# 一份人能读懂的需求文档

`PROJECT-REQUIREMENTS.md` 要说清楚：

- 原始想法和一句话目标；
- 使用者与使用场景；
- 第一版可见结果；
- 必须能力与不做范围；
- 已有输入和现实限制；
- 可以真实检查的验收标准；
- 待验证问题。

---

# 好需求会告诉 Codex 在哪里停

“做一个好用的网站”无法验收。

“在手机和电脑上打开首页，都能看到作品、简介和联系方式；不做登录、支付和后台”可以验收。

```text
清楚的结果 + 明确的边界 + 可观察的证据
```

---

# 人负责确认，Codex 负责整理

Codex 可以：

- 发现遗漏和冲突；
- 给出推荐选择；
- 把讨论整理成结构化文件。

人必须：

- 决定第一版做什么、不做什么；
- 否定不符合自己想法的建议；
- 检查并确认最终需求文档。

---

# 需求确认后，才进入实施

```text
PROJECT-REQUIREMENTS.md
        ↓
Codex 检查现有项目事实
        ↓
PROJECT-PATH.md
        ↓
NEXT-TASK.md
        ↓
确认后实现第一个可见小步骤
```

新的 Codex task 应先读需求和现有文件，不应凭聊天记忆直接开工。

---

# 课堂最低完成线

必须完成：

- 一轮真实的 Grill Me 追问；
- 一份本人确认的 `PROJECT-REQUIREMENTS.md`；
- 能说清第一版结果、不做范围和验收方式。

有余量再继续：实施路径 -> 第一个任务 -> 第一个可见结果。

没有在课堂写完代码，不等于本单元失败。

---

# 从自己的需求继续走下去

前面的课程提供了方法：

```text
用 Workspace 留下事实
用 Skill 保存做法
用 GitHub 管理代码变化
用检查结果判断是否完成
```

最后带走的不是一个课堂 Demo，而是一份可以继续交给 Codex 的真实需求。
