# Unit 5：把模糊想法变成可实施的需求

## 这次要完成什么

你不需要先把想法说得专业，也不需要在课堂上完成整个项目。

这次只完成一件关键的事：使用 `grill-me`，让 Codex 一次问一个真正影响项目的问题。你负责回答、纠正和做选择，最后得到一份自己看得懂、Codex 也能据此实施的需求文档：

```text
<个人 Obsidian 知识库>/Learn/Agent 101/Projects/<项目名>/PROJECT-REQUIREMENTS.md
```

课堂时间足够时，可以继续让 Codex 生成实施路径，并实现第一个可见的小步骤；时间不足时，需求文档就是本单元的完整最低产物。

## Grill Me 在这里做什么

`grill-me` 会调用它依赖的 `grilling`。它不会替你决定要做什么，而是帮助你发现那些如果不先想清楚，Codex 很容易做错的问题。

它应该这样工作：

```text
你的原始想法
-> 一次只问一个问题
-> 每次给一个可否定的建议
-> 根据你的回答继续追问
-> 复述已经确认的决定
-> 你纠正并确认
-> 生成需求文档
```

追问不是越多越好。当下面这些内容已经足够清楚，可以开始第一版时，就应该停止继续追问：

- 为什么要做，想改变什么；
- 给谁使用，在什么场景使用；
- 第一版能看见或使用的结果；
- 必须有的能力；
- 明确不做什么；
- 已有材料、工具和限制；
- 怎样判断第一版做对了；
- 哪些未知问题可以留到实施时验证。

## 开始前准备 Skill

先按 [课程 Skill 地图](../../../SKILLS.md) 准备 `grill-me` 和 `grilling`。两者缺一时不要假装已经使用 Skill；可以由老师现场补齐后再继续。

安装或确认完成后，新开一个 Codex task，再使用下面的第一段提示词。

下面两段提示词都直接放在人读页中，可以一键复制给 Codex，不需要再打开单独的提示词文件。

## 第一段：把想法问清楚并生成需求文档

把自己的想法填在最后一行，再复制整个代码块。

```text
请带我完成 Agent 101 的 Unit 5。当前目标不是马上写代码，而是把我的模糊想法变成一份可实施的需求文档。

请先读取：
- 课程 repo 根目录的 SKILLS.md
- 当前 Unit 的 STUDENT.md 和 AGENT-TASK.md
- 当前 Unit 的 templates/PROJECT-REQUIREMENTS.md

然后严格按以下方式协助：
1. 检查 grill-me 和它依赖的 grilling 是否可用；缺少任一个就报告，不要假装已使用。
2. 确认我的个人 Obsidian 知识库绝对路径，以及需求文档准备写入的位置。课程 repo 保持只读。
3. 明确使用 grill-me 追问我的原始想法。一次只问一个问题，等我回答后再继续；每次给一个推荐答案和简短理由，但允许我采用、修改或否定。
4. 优先追问会改变第一版范围的问题。已经从我的回答或已授权文件中得到答案的内容，不要重复问；低影响细节不要无限追问。
5. 当目标、使用者与场景、第一版结果、必须能力、不做范围、已有输入与限制、验收标准和主要未知项已经足够支持第一版时，主动告诉我可以停止追问。
6. 写文件前，先用人话复述已确认决定、仍待验证的问题和你建议的第一版边界。只有我明确确认后，才能生成正式需求文档。
7. 按 PROJECT-REQUIREMENTS.md 模板写入：<个人 Obsidian 知识库>/Learn/Agent 101/Projects/<项目名>/PROJECT-REQUIREMENTS.md。目标文件已经存在时不要覆盖，先报告并让我决定。
8. 写完后让我亲自检查：删掉一个不需要的内容、改写一个不准确的内容，或明确确认全部保留。根据我的反馈更新后，再汇报实际路径和仍待确认项。

不要开始完整开发，不要创建代码 repo，不要 commit、push 或删除文件。

我的原始想法：<在这里写一句自己的原话>
```

## 追问时怎么参与

只回答当前问题，不需要一次把所有事情都说完。

当 Codex 给出推荐答案时，可以直接这样回答：

- “采用，因为这就是我想要的。”
- “方向对，但把第一版再缩小一点。”
- “不采用，我真正关心的是……”
- “我现在不知道，把它记为实施时要验证的问题。”

最后一种回答同样有效。需求文档不要求消灭所有未知问题，而是要区分：哪些已经决定，哪些需要通过下一步实验才能知道。

## 怎样判断需求文档够清楚

打开 `PROJECT-REQUIREMENTS.md`，不用看聊天记录，尝试回答：

1. 这是给谁解决什么问题？
2. 第一版到底会出现什么可见结果？
3. 第一版必须做到哪几件事？
4. 哪些诱人的功能明确不做？
5. 用什么证据判断第一版完成？
6. Codex 开始实施前，还有什么必须先检查？

如果其中两项说不清楚，就回到 `grill-me` 再追问；如果都能说清楚，课堂最低目标已经完成。

## 第二段：把需求文档交给 Codex 实施

这一段是课堂有余量或课后继续使用的入口。建议新开一个 Codex task，并把工作目录切到准备实施项目的位置。

Codex 不能只看到需求文档就立刻大规模写代码。它要先检查当前环境、提出实施路径，并等你选择第一步。

```text
我要继续实施已经确认的需求。请先不要修改文件，也不要 commit 或 push。

需求文档绝对路径：<填写 PROJECT-REQUIREMENTS.md 的绝对路径>
准备工作的项目路径：<已有项目就填绝对路径；还没有就写“尚未创建”>

请按顺序进行：
1. 读取需求文档，用不超过 300 字复述第一版目标、必须能力、不做范围和验收标准。
2. 如果已有项目，检查它的 README、AGENTS.md、目录结构、git status 和现有运行方式；能从文件确认的事实不要问我。如果尚未创建项目，先提出一个最小项目位置和形式，不要直接创建。
3. 列出需求与当前事实之间的差距，把不确定内容标成“需要验证”，不要自行补成事实。
4. 生成一条从现在到第一版可见结果的实施路径，并推荐一个最小、可逆、可检查的第一步。说明会修改哪些文件、怎样验证、失败时在哪里停止。
5. 等我确认实施路径和第一步后，才开始修改。每完成一个小步骤就运行相应检查，并让我亲自查看结果。
6. 把实施路径和第一个任务分别写到需求文档同目录的 PROJECT-PATH.md 和 NEXT-TASK.md；代码或实际产物放在项目路径，不写进课程 repo。

如果课堂时间不足，只完成步骤 1-4 并保存实施路径，不开始编码。不要扩张需求文档没有承诺的功能。
```

## 文件放在哪里

```text
<个人 Obsidian 知识库>/Learn/Agent 101/Projects/<项目名>/
  PROJECT-REQUIREMENTS.md   课堂最低产物
  PROJECT-PATH.md           可选：实施路径
  NEXT-TASK.md              可选：第一个实施任务

~/Projects/<项目名>/
  需要写代码时才使用的独立项目目录和 Git repo

<个人 Obsidian 知识库>/Projects/AI Agent Learning Workspace/
  只读课程入口和模板
```

需求文档与代码可以放在不同位置。Codex 可以同时读取它们，但不能因此把个人需求或代码写回课程 repo。

## 完成标准

课堂最低完成：

- `PROJECT-REQUIREMENTS.md` 已写入个人 Obsidian。
- 文档能回答目标、使用者与场景、第一版结果、必须能力、不做范围、限制和验收标准。
- 重要未知项被明确标成待验证，没有被 Codex 编造成事实。
- 你确认过追问后的复述，并亲自删、改或确认过最终文档。
- 课程 repo 保持只读。

扩展完成：

- Codex 已读取需求和当前项目事实，生成 `PROJECT-PATH.md` 与 `NEXT-TASK.md`。
- 你已经确认第一个最小步骤及其验证方式。
- 只有在时间允许并得到确认时，才实现并检查第一个可见结果。
